# Decryption service invariants

Each ID names a guarantee and links to direct assertions. Keep IDs stable.
A recorded rehearsal is distinct from an automated test and applies only to its
recorded configuration. Track uncovered release controls in the [internal audit](AUDIT.md).

## Decryption service

| ID | Invariant | Coverage |
| --- | --- | --- |
| SPR-CORE-01 | Only a signer-capable Solana address gets service keys. | Lookup and decrypt reject malformed, off-curve, and small-order addresses. Forged, missing, and noncanonical signatures fail even for empty batches. [Owner authorization](../enclave/tests/unit/owner_authorization.rs) |
| SPR-CORE-02 | The address and deployment note seed determine the service keys. | Fixed derivation vectors, address and seed separation, and agreement across replicas. [Derivation](../enclave/tests/unit/key_derivation.rs) · [Release binding](../enclave/tests/unit/release_binding.rs) |
| SPR-CORE-03 | The owner approves the ordered batch for one network and release. | A change to the signer, request ID, item field, item order, item count, network, or response key invalidates approval. The enclave rejects mismatched release pins, unsupported versions, and unknown fields. Rust and TypeScript agree on the digest and signed Solana message. [Owner authorization](../enclave/tests/unit/owner_authorization.rs) · [Release binding](../enclave/tests/unit/release_binding.rs) · [Rust vectors](../protocol/tests/unit/decryption_request_binding.rs) · [SDK vectors](../sdk/tests/protocol/decryption.test.ts) |
| SPR-CORE-04 | Only the signed response key opens the reply, including after replay. | A second key cannot open the reply or replace the signed key. Invalid and compressed response keys fail. [Response privacy](../enclave/tests/unit/response_privacy.rs) |
| SPR-CORE-05 | The enclave uses only the verified signer's viewing key. | An output for another address yields unrelated bytes. Wrong ephemeral key encoding, low-order points, malformed salt, and invalid slots fail the entire batch. Ring deposits use their own cipher domain and require slot zero. [Output handling](../enclave/tests/unit/output_handling.rs) |
| SPR-CORE-06 | Batch and byte limits apply before work crosses the next boundary. | The enclave accepts 256 items, rejects 257, and bounds HTTP bodies and encrypted results. The SDK rejects malformed slots, labels and salts before approval and splits at 256 or on the serialized byte limit before signing. It preserves order and rejects incomplete results. [Enclave batches](../enclave/tests/unit/output_handling.rs) · [HTTP limits](../enclave/tests/unit/http_and_ping.rs) · [Result limit](../enclave/tests/unit/app_proof_signature.rs) · [SDK batching](../sdk/tests/client/items.test.ts) · [Item validation](../sdk/tests/client/keys.test.ts) · [Before signing](../sdk/tests/client/decryption.test.ts) |
| SPR-CORE-07 | The SDK opens only the authenticated reply to its request. | Wrong proof type, version, signature, request ID, request digest, result digest, operation, scheme, or signing replica fails. | SPR-CORE-08 | Decrypted notes must match their indexed commitments. | The SDK opens empty and nonempty batches with separate approvals. | SPR-CORE-10 | The enclave serializes plaintext replies into one bounded, zeroizing output buffer before encryption. | Both reply variants keep their canonical wire bytes. Tests cover empty items, hex chunk boundaries and the plaintext size ceiling. [Reply encoding](../protocol/tests/unit/decryption_result_encoding.rs) · [Encrypted reply limit](../enclave/tests/unit/app_proof_signature.rs) |
